# Research methods (Phase 6, v0.6)

Generated by `python scripts/gen_research_methods.py`: prose is written in that script; every table is produced from the code and from running the methods on the synthetic fixtures `syn-var-1` (injected brightness change) and `syn-hpm-1` (injected high proper motion). Fixture results are known-answer checks of the methods, **not facts about the sky**.

None of these methods measures anything new. They organise, check and plan around the deterministic analysis (`analysis.py`, `science/`), whose methods are documented in `SCIENTIFIC_METHODS.md` and `DISCOVERY_METHODS.md`. No method here produces a probability or a score.

## SESSION-1 — research session

A session (`skytrace.research_session/1`) holds the question, attached runs (by content hash), hypotheses with versions, notebook blocks, annotations, plans, experiments, missions, workflows, examined pairs and an append-only history. It is validated by SCHEMA-1 (the same declarative schema in `schema.py` and `web/js/schema.js`) and hashed as SHA-256 of its SKY-CANON-1 text without `content_hash`. Imports whose stated hash differs are refused; an import never overwrites an existing id. Saved 0.5 records migrate into sessions; the original record is kept.

* Size limit: 1,000,000 bytes of canonical text.
* Notebook block types (13): heading, paragraph, observation, measurement, evidence, hypothesis, experiment, figure, warning, parameters, citation, question, conclusion.
* Reference kinds: observation, measurement, claim, graph_node, hypothesis, user_hypothesis, experiment, figure, run, dataset, pair, test, challenge, scenario, opportunity, twin.
* Plan-step statuses: suggested, ready, running, completed, blocked, failed, needs_review.

## COMPAT-1 and SEQ-1 — observation compatibility and sequences

COMPAT-1 reads the WLMATCH-2 decisions already logged in the record and lays them out as a matrix; it never re-decides a pair. Reason codes:

| Code | Meaning |
|---|---|
| accepted | wavelength-matched: brightness may be compared (WLMATCH-2) |
| wavelength_mismatch | same detector, but the wavelengths at the target differ by more than the tolerance |
| different_detectors | different detectors sample different wavelength ranges |
| different_release | different archive releases are not combined for photometry |
| unusable_measurement | one of the two measurements is not usable (failed or flagged photometry) |
| not_measured | one of the two observations has no measurement in this run |

Exposures are grouped into visits by time. SEQ-1 sequences are sets of observations on one detector in which every pair is accepted (cliques of the accepted-pair graph, built greedily in time order); playback runs only over a sequence, never interpolates, and states when a sequence spans only two visits. Coverage gaps are intervals of at least 30 days between visits on a detector. Duplicates are observations whose files share a SHA-256.

| syn-var-1 | 48 | 1128 | 46 | 6 | 4 / 2 | 18 | 0 |
| syn-hpm-1 | 48 | 1128 | 43 | 6 | 4 / 2 | 18 | 0 |

## DQ-1 — data-quality checks

Each check states its rule and reports one of: invalid, incompatible, not_available, not_checked, valid. The outcomes are listed in order of severity; a check's outcome is the most severe of its items. There is **no overall score**: the checks are reported separately because they are not commensurable.

| Check | Name | Rule |
|---|---|---|
| DQ-FILES | File integrity | every file's SHA-256 equals the manifest |
| DQ-META | Required observation metadata | obs_id, release, detector, mid-time and file are present and the file is in the manifest |
| DQ-VALUES | Measured values | fluxes finite, errors positive, wavelength within the SPHEREx range, bandwidth and centroid errors positive |
| DQ-UNITS | Units | image MJy/sr and variance (MJy/sr)^2, as the photometry assumes |
| DQ-FLAGS | Quality flags | FLAGPOL-1: no rejecting flag bits inside the aperture; bits the header does not define cannot be checked |
| DQ-PAIRS | Comparable observation pairs | WLMATCH-2 decisions, with the reason for each rejection |
| DQ-CAL | Calibration information | ≥ 3 wavelength-matched reference stars per compared pair (PAIRDIFF-2), and a calibration check |
| DQ-PROV | File provenance | every manifest file records its source, origin and retrieval time |
| DQ-STEPS | Processing steps | every logged step completed; failed, skipped or rejected steps are listed with their reason |
| DQ-ASTRO | Astrometric usability | an exposure is usable for the motion fit when its plate solution and target centroid succeed |
| DQ-RECORD | Record integrity | the record's content hash recomputes |

| Fixture | DQ-FILES | DQ-META | DQ-VALUES | DQ-UNITS | DQ-FLAGS | DQ-PAIRS | DQ-CAL | DQ-PROV | DQ-STEPS | DQ-ASTRO | DQ-RECORD |
|---|---|---|---|---|---|---|---|---|---|---|---|
| syn-var-1 | valid | valid | valid | valid | invalid | incompatible | not available | valid | incompatible | not available | valid |
| syn-hpm-1 | valid | valid | not available | valid | invalid | incompatible | not available | valid | incompatible | not available | valid |

The fixtures' `invalid` and `incompatible` outcomes are deliberate: the fixtures include flagged exposures and wavelength-mismatched pairs so that the checks have something to find. Injected defects (altered hashes, missing fields, wrong units) are tested in `tests/unit/test_research_os.py`.

## LEDGER-1 — evidence ledger

For each claim the ledger counts direct evidence items, wavelength-matched comparisons, observations and detectors reached from the claim in the evidence graph. A claim resting on one item is flagged as such; one linked item is never reported as full support. Absence outcomes (insufficient_evidence, no_motion_at_sensitivity, no_significant_change, spectral_difference_only) are statements about sensitivity and are not flagged for lacking positive support. Contradictions are found by four fixed rules: C1 raw significance at or above the threshold but the calibrated, error-scaled one below (or the reverse); C2 two motion fits differing by more than 3σ; C3 measured motion differing from the catalogue by more than 3σ; C4 tests of one explanation disagreeing.

## RADAR-1 — Discovery Radar

The radar lists **research opportunities**, not detections. Each item states what it proposes, why, the evidence, the data it needs, the action that would carry it out, what it cannot establish, and whether it can run here and now.

```
Signals (fixed rules over the record, COMPAT-1, DQ-1, LEDGER-1 and HYPO-1 outputs):
  R1 significant pairs to inspect      matched pairs at or above the detection threshold (calibrated where possible)
  R2 unresolved explanations           explanations whose implemented tests are inconclusive
  R3 untestable explanations           explanations whose every test needs a method that is not implemented
                                       (a test that is implemented but not applicable here is not an opportunity)
  R4 unused measurements               usable measurements that are in no accepted pair
  R5 sensitivity not yet examined      STAB-1 not run for this target (the interface clears it once run)
  R6 evidence conflicts                LEDGER-1 contradictions
  R7 data-quality gaps                 DQ-1 checks whose outcome is invalid or not available
  R8 unobserved intervals              coverage gaps between visits (needs new observations)
  R9 provenance gaps                   LEDGER-1 completeness gaps other than expected ones
```

Ranking: runnable items first, then signal order R1 → R6 → R2 → R5 → R7 → R4 → R3 → R9 → R8; ties keep the record's order. The order is a stated convention, not a computed value.

## EXP-1 — Experiment Studio

Templates and their pass criteria (at most 8 analysis runs per experiment):

| Template | Title | Criterion |
|---|---|---|
| parameter | Parameter experiment | each run's outcome categories equal the baseline's |
| sensitivity | Sensitivity (STAB-1 set) | each run's outcome categories equal the baseline's |
| reproducibility | Reproducibility | two independent executions give identical content hashes |
| method_comparison | Method comparison | PAIRDIFF-1 and PAIRDIFF-2 agree on detection for each calibrated pair; the two motion fits agree within 3σ per axis |
| negative_control | Negative control | the effect absent by construction is not detected |
| robustness | Robustness at parameter bounds | every run completes and reports all three outcomes |

Robustness settings (the bounds the server accepts): aperture 1.0 px (lower bound); aperture 5.0 px (upper bound); tolerance 0.1 channel (lower bound); tolerance 1.0 channel (upper bound); epoch clip 2σ (lower bound); epoch clip 10σ (upper bound).

## WF-1 — workflows

A workflow (`skytrace.workflow/1`) declares its targets (≤ 4), steps (≤ 10) and at most 24 executions in total; every step is a registered action and dependencies must precede. Execution keeps a per-item record (status, error, result summary); cancellation stops before the next step and keeps completed items; retry runs only items that failed or were cancelled. Templates: Quality and evidence review, Reproducibility audit, Sensitivity sweep.

## Browser-side methods (FIG-2, KG-1, NOTE-1)

* **FIG-2** (`web/js/figurestudio.js`): figures drawn only from recorded values — observation timeline, flux per sequence, z histogram, positions, data-quality outcomes, sensitivity. Each states its title, units, data source, method and the run's content hash; SVG export embeds that metadata. No PDF export is offered.
* **KG-1** (`web/js/kg.js`): links saved records and sessions only by stored facts — K1 names the same target, K2 identical content hash, K3 a session uses a saved run, K4 same analysis version, K5 the same non-clean data-quality category. With fewer than two records or sessions it shows an empty state. No relationship carries a confidence value.
* **NOTE-1** (`web/js/notebook.js`): blocks are text (yours) or references to recorded items, resolved against the active run when shown and exported; assistant drafts stay labelled until accepted. Markdown export labels every block [you] / [recorded] / [draft]; the session package is a deterministic stored ZIP (`web/js/zipstore.js`).

Browser ports checked against this code by parity tests: planner (its rules are served from `/api/specs`, so both use one table), missions, workflows, session validation and hashing (`tests/unit/test_research_os.py`, `tests/unit/test_research_session.py`).
